## Hard rules for both layers
1. Each layer is behind its own flag in `RadarCore.Configure`, **off by default**. Off = not one line of the layer runs, not even the probe for the handle.
2. Each layer **self-disables with a note in Hook Status** when the runtime does not match: handle not found, type shape different, Emit failed, zero events after N stages. Hook Status gains one segment per layer, e.g. `stage log: live (312 entries)` / `stage log: not available (CompoundLoggingEngine not found from roots)` / `stage log: off`. Same for `data chain:`.
3. Zero effect on execution. Nothing the layer does can throw into the robot: every entry point is try/catch, every reflection call guarded, bounded in time (probe ≤ 2 s, data item capture ≤ 1 s) and in size. The DB logging engine is not touched, not removed, not reordered; the database stays on Errors Only.
4. The self-test must PASS under mono, where none of the Blue Prism types exist. There the layer must report "not available" cleanly, and the Emit path must be exercised against a stand-in abstract class defined inside the self-test, so the subclass generation is proven here and only the handle lookup is proven on the bank machine.
5. Never read or store credentials; mask `/password`-style tokens as RadarDiscover does. Mask parameter values that look like IBAN, CNP (13 digits), or card PAN (13–19 digits, Luhn) before they reach the ring.

## Design: one handle feeds both layers
The one thing to find at runtime is **this session's `CompoundLoggingEngine`** (equivalently its `BluePrismProcess`). Find it from a static root in AutomateAppCore/AutomateProcessCore (the listener's runner list is the expected path; match the `RunnerRecord` whose thread is `Thread.CurrentThread`, then its process, then its logger). Resolve every field/property by name from what discover.txt shows, with a fallback by type (first field whose type is assignable to the wanted type). Do the lookup once per session, at Configure, under a 2 s budget; cache the result in the session's Ring.

**Layer 1, Stage Log.** Build at runtime, with `System.Reflection.Emit` (BCL), a subclass of `LoggingEngine` that overrides every abstract method and forwards `(methodName, info, stage, args[])` to a static `RadarCore.OnStageEvent(...)`. Append one instance to the compound engine's engine list (find the list field by type; keep the DB engine first). `OnStageEvent` records into a per-session bounded ring (default 500, separate from the existing 50-entry trail): one entry per Prologue (start) completed by the matching Epilogue (end, result/outputs). Columns as in `clsSessionLogEntry`; read stage name, stage type, page name and the owning process/object name from the `ProcessStage` instance by reflection; parameters from the `ArgumentList` as `name=value` into an XML-ish `AttributeXml` string like the real export, masked. On Dump the section `--- stage log (last N stages, oldest first) ---` goes into incident.txt and a `"stage_log": [...]` array into incident.json. Ignore `LogInfo` inhibit flags on purpose: Radar records what the DB engine declines. If the process stops calling engines for inhibited stages, the counter stays at 0 and the layer reports `not available (no events after N stages)`.

**Layer 2, Data Chain.** The chain page → sub-page → object action → stage comes from Layer 1's event stream, no stack parsing: push on `Process/SubSheet/Object/ActionPrologue`, pop on the matching `Epilogue`; the current stage is the last Prologue without Epilogue. At Dump time, for each frame in the chain, enumerate that page's data and collection stages from the `BluePrismProcess` the frame's stage belongs to (`stage.Process` or the equivalent member discover.txt shows), read each value as text (collection as row count plus the first 5 rows), mask, bound at 1 s / 200 items. Written as `--- data chain at failure ---` in incident.txt, `"data_chain": [ { "process", "page", "stage", "items": {...} } ]` in JSON, outermost first. The existing `Data Items` input stays and is written as before; when Layer 2 is live it is optional.

Hook Status wording is the contract: `stage log: off | live (n entries, m stages) | not available (<reason>)` and `data chain: off | live (depth d) | not available (<reason>)`; `live` only after the first event has actually arrived.

## Self-test addition (core/RadarSelfTest.cs)
Follow the file's conventions: `Ok(name, cond, info)`, PASS/FAIL lines, exit code, cleanup of the temp root. Add a section `---- the stage log and data chain layers ----` that proves, under mono:
- both flags off by default: Hook Status says `stage log: off` and `data chain: off`, and no probe ran (a counter you expose stays 0);
- with a flag on and no Blue Prism types present, Hook Status says `not available (` with a reason, Dump still writes a full folder, incident.json still parses, and `stage_log` / `data_chain` are present and empty;
- the Emit path: define a stand-in `abstract class FakeLoggingEngine` with a ctor taking an object, 4–5 abstract methods shaped like the real ones (`ActionPrologue(object info, object stage, string objectName, string actionName, object inputs)`, an Epilogue, `LogError`, one with a `ProcessValue`-like object), call the same emit routine Radar uses against it, instantiate the result, call the abstract methods through the base type, and assert the events arrived in the ring with the right method name, stage name and masked parameters;
- masking: an IBAN, a 13-digit CNP and a Luhn-valid 16-digit PAN are masked in parameters; a 13-digit non-CNP-looking number and short numbers are left alone;
- chain push/pop: a sequence of fake Process/SubSheet/Action/Code Prologue/Epilogue events yields the expected chain, and Dump writes it outermost first;
- bounds: 1000 fake stage events keep the ring at its capacity with a dropped count.
